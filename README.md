# Тестовое задание

Нужно ускорить ночную синхронизацию сущностей из CRM в Postgres.
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.
Сейчас прогон делает отдельный запрос и commit на каждую сущность
и в конце ещё раз читает всю таблицу.
## Некоторые правила бизнес-логики
- Покупатель без логина пропускается.
- Покупатель ищется по id покупателя в CRM, иначе по логину среди уже сохранённых сделок.
  Если по логину нашлось больше одной записи, совпадение не используется.
- Сделка ищется по id сделки в CRM, иначе по логину среди покупателей.
  Если это две разные записи, они сливаются в ту, что нашли по сделке; вторая удаляется.
  Если не нашлось ничего, создаётся новая запись.
- После успешного полного прохода удаляются покупатели и вложенные
  сущности, которых не было в этой выгрузке, в том числе с «удалить» в имени.
- Если сбор прервался, удаление не запускается.
Падения и расхождения кода с этим списком нужно поправить.
Формат JSON в полях можно сохранить.
## Ограничения
- Python >= 3.9, Flask, SQLAlchemy, PostgreSQL.
- Celery, брокер и боевой API поднимать не нужно.
- Новые сервисы не добавлять. Схему хранения можно менять.
- Ночной прогон ищет покупателя и сделку по id CRM и по логину.
  Другие части системы ищут покупателя или сделку по точному логину и по названию.
  этот поиск писать не нужно, но выбранная схема должна его выдерживать.
  Также нужно поддерживать связь сделка-покупатель.
- Способ реализации на ваше усмотрение, правила выше обязательны.
Полный объём локально гонять не нужно: клиента CRM в репозитории нет.
Оцените память процесса и число запросов к Postgres на указанных цифрах.
## Результат
Точка входа не изменилась: `collect_leads_customers(is_full=True)`.

### Что было дорого
В исходной реализации для каждой сущности выполнялись отдельный SQL-поиск и `commit()`. Для 20 тыс. покупателей и 50 тыс. сделок это давало порядка ~70k+ обращений к PostgreSQL и столько же транзакций, плюс повторное чтение всей таблицы на этапе очистки.

### Дополнительные затраты и ошибки
- В конце синхронизации таблица `abstract_customer` повторно читалась целиком.
- Поиск по логину мог загружать все совпадения, хотя достаточно различить 0, 1 или >1.
- JSONB обновлялся отдельными `jsonb_set`-операциями.
- При объединении двух агрегатов `lead_action()` возвращал `None`, после чего вызывающий код обращался к `abc_customer.id`.
- Ошибки обработки сделок подавлялись, но после них всё равно могла начаться очистка.
- В `filter_merge_abstract_customer()` использовалась неверная переменная при фильтрации; `commit()` выполнялся внутри цикла.

### Что изменено

`main.py`
- Существующие агрегаты загружаются одним `SELECT` в начале синхронизации.
- На их основе строятся индексы в памяти: CRM id покупателя, CRM id сделки, логины покупателей и логины сделок.
- CRM id имеет приоритет. Поиск по логину используется только при единственном совпадении; неоднозначное совпадение игнорируется.
- При конфликте между найденным по id сделки агрегатом и найденным по логину покупателя агрегаты объединяются в агрегат, найденный по id сделки; второй удаляется.
- JSON-массивы меняются в памяти; поштучных SQL-поисков и `commit()` на сущность больше нет.
- Каждые 500 обработанных сущностей вызывается `session.flush()` (отправка SQL без фиксации транзакции).
- Один `session.commit()` в конце успешного прохода фиксирует и изменения, и очистку.
- Очистка выполняется только после успешной обработки обоих потоков CRM. Любая ошибка приводит к `rollback`: деструктивное удаление не фиксируется.
- Удаление отсутствующих сущностей и пустых агрегатов идёт по уже загруженным объектам, без повторного `SELECT` всей таблицы.
- Для `is_full=False` сохранены исключения по статусам; очистка не выполняется.

`abstract_customer.py`
- Поиск по логину ограничен двумя результатами: этого достаточно, чтобы отличить 0, 1 и >1 совпадения.
- Обновление JSON-массивов и объединение элементов выполняются в Python.
- Обработка отсутствующих `custom_fields_values` стала безопасной.

`amocrm.py`
- Безопасная обработка отсутствующих пользовательских полей (`custom_fields_values or {}`).
- Пагинация завершается, если API не вернул ссылку на следующую страницу.

### Что оставлено и почему
- Схема PostgreSQL и `models.py` не менялись. Ускорение за счёт алгоритма синхронизации и работы в одной транзакции, а не за счёт новой модели данных.
- Формат JSONB сохранён: не нужно мигрировать данные и менять потребителей `AbstractCustomer`.
- Поля `general.login`, `general.name` и `api_value` сохранены. Другие части системы по-прежнему могут искать по точному логину и названию; связь сделка–покупатель в одном агрегате сохраняется.

Один `commit()` в конце выбран намеренно: обновления и очистка атомарны. Если прогон падает, транзакция откатывается, частичных записей и «полуочистки» нет. Следующий полный запуск обрабатывает сущности заново.

### Оценка запросов и памяти

Для 20 000 покупателей и 50 000 сделок (порядок величины):

**Запросы к Postgres**
- ~1 `SELECT` всех агрегатов в начале.
- Во время обхода CRM — без `SELECT` на каждую сущность (поиск только по in-memory индексам).
- `flush` каждые 500 сущностей: порядка ~140 `flush` (SQL уходит в БД, транзакция ещё не зафиксирована).
- 1 финальный `commit` (включая очистку).
- Число фактических `INSERT` / `UPDATE` / `DELETE` зависит от того, сколько агрегатов изменилось, создано, слито или удалено; один `flush`/`commit` может содержать много DML.

Итого к Postgres: порядка **O(1) чтений таблицы + O(число изменённых агрегатов) записей**, а не O(число сущностей CRM) как в исходнике (~70k+ round-trip).

**Память процесса**
- В RAM держатся все загруженные строки `AbstractCustomer` (JSONB-документы) + индексы по CRM id и логинам + множество `seen`.
- Сложность: O(число агрегатов + суммарный размер JSONB + число сущностей в индексах).
- При типичном размере агрегата с `api_value` в единицы–десятки КБ на 20–50k сущностей это **сотни МБ** рабочего набора, а не гигабайты и не «по запросу на сущность». Пик зависит от объёма вложенного `api_value` и числа контактов/компаний.
